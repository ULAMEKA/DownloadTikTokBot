# Ускорение конвейера загрузки видео

Дата: 2026-08-30
Статус: проект спецификации для проверки
Область: локальный код DownloadTTBot; развёртывание на production не входит

## Контекст

Даже первое небольшое видео воспринимается как медленное. Текущий путь содержит
несколько независимых задержек:

- рекламная заглушка удерживает готовое видео 15 секунд;
- private-путь может трижды извлекать метаданные одного URL: для меню качества,
  для поиска кеша и внутри фактической загрузки;
- каждый файл проходит probe, FFmpeg-remux или transcode и повторный probe, даже
  если это уже совместимый MP4 с H.264/AAC;
- при наличии `STORAGE_CHAT_ID` private/group-видео сначала полностью загружается
  в storage-канал и только затем доставляется пользователю по `file_id`;
- один FIFO-воркер обрабатывает и обычные видео, и длительное распознавание музыки;
- одна SQLAlchemy-сессия живёт во время сетевых запросов, FFmpeg и Telegram I/O;
- пустая очередь опрашивается раз в секунду;
- в текущем `master` включён SQLAlchemy `echo=True`, а `bot.log` не ограничен
  ротацией.

## Цели

1. Сократить рекламную задержку новых загрузок с 15 до 5 секунд.
2. Доставлять валидный кеш без постановки в `DownloadQueue`, без рекламной
   задержки и без обращения к downloader/FFmpeg/storage.
3. Свести успешный cache-miss к одной extractor-фазе `yt-dlp` в обычном пути.
4. Не запускать FFmpeg для уже совместимого безопасного MP4.
5. Не держать БД-сессию открытой во время внешних сетевых и файловых операций.
6. Давать обычным видео приоритет над ещё не начатым распознаванием музыки.
7. Убрать до одной секунды ожидания пустого polling без потери восстановления
   очереди после перезапуска.
8. Сохранить работу на VDS с 512 МБ RAM: одновременно выполняется не более одной
   тяжёлой media-задачи.
9. Добавить измеримые этапы, чтобы дальнейшие оптимизации основывались на p50/p95,
   а не на общей длительности запроса.

## Не цели

- Несколько параллельных скачиваний или FFmpeg-процессов.
- Снятие глобального ограничения `yt-dlp` до появления production-метрик.
- Изменение opt-in UX распознавания музыки.
- Поддержка нескольких процессов бота; документированное ограничение на один
  экземпляр сохраняется.
- Автоматическое развёртывание, перезапуск production или изменение live-БД.

## Архитектурные решения

### 1. Рекламная задержка

`AD_DISPLAY_SECONDS` меняется с 15 на 5. Таймер создаётся только для реального
cache-miss, когда бот показывает рекламную заглушку перед новой загрузкой.

Cache hit не создаёт рекламную заглушку и не вызывает ожидание. В private-чате
видео отправляется сразу после выбора режима; в группе и inline-режиме — сразу
после локальной проверки кеша.

### 2. Локальная идентификация и cache fast path

Добавляется чистый helper, который получает cache identity из уже очищенного
канонического URL без `yt-dlp`:

- TikTok `/video/<id>` и `/photo/<id>` используют числовой ID;
- Instagram `/reel/<shortcode>` и `/reels/<shortcode>` используют shortcode;
- короткая TikTok-ссылка сначала проходит существующую канонизацию;
- если identity локально определить нельзя, обработчик без ошибки продолжает
  обычный queue-path.

`VideoCache` расширяется nullable-полями `source_url` и `likes`. Миграция в
`init_db.py` идемпотентно добавляет их существующим установкам. Старые строки
остаются валидными: для них используется текущая ссылка, а лайки могут быть
не показаны.

Общий cache lookup возвращает неизменяемый снимок с `cache_key`, `file_id`,
описанием, source URL и лайками. Он вызывается:

- в `handle_download_option()` до `list_video_qualities()`;
- в group-handler до создания photo-placeholder и enqueue;
- в `chosen_download()` до enqueue и обновления позиции;
- повторно воркером перед extractor-фазой, чтобы учесть кеш, появившийся между
  enqueue и началом обработки.

Private сохраняет существующее меню режимов. Cache hit доставляется по выбранным
параметрам `without_description` и `has_spoiler`, но не создаёт queue row.
Group отвечает кешированным видео на исходное сообщение. Inline редактирует уже
созданный inline-placeholder через Telegram `file_id`.

### 3. Невалидный Telegram file_id

Удалять cache row разрешено только при Telegram-ошибке, явно означающей
невалидный или недоступный `file_id`. Forbidden, rate limit, временная сеть,
ошибка подписи и прочие Telegram-ошибки не должны разрушать кеш.

При подтверждённо невалидном `file_id` обработчик:

1. удаляет соответствующую cache row в короткой транзакции;
2. продолжает тот же запрос по обычному cache-miss пути;
3. создаёт рекламную заглушку и ставит новую загрузку в очередь;
4. не просит пользователя повторно отправлять ссылку.

Классификация ошибки изолируется в одном helper и покрывается тестами на
положительные и отрицательные сообщения Telegram.

### 4. Одна extractor-фаза и повторное использование info JSON

Вводится результат инспекции медиа, содержащий очищенные поля для приложения и
санитизированный info dict `yt-dlp`. Установленный `yt-dlp` поддерживает
`YoutubeDL.sanitize_info()` и `download_with_info_file()`; последний при
устаревшем info-файле сам возвращается к исходному `webpage_url`.

Private cache-miss выполняет инспекцию для существующего меню качества один раз.
Пока пользователь видит меню качества, санитизированный info dict хранится в
соответствующем `PendingDownload` и удаляется вместе с ним по существующему TTL.
При enqueue snapshot сначала записывается во временный файл, затем через
`os.replace()` атомарно становится `videos/<job>.info.json`. Воркер скачивает из
него с выбранным `format_id`, не извлекая страницу повторно.

Group/inline cache-miss не требуют меню качества. Воркер выполняет одну инспекцию,
проверяет cache identity из результата и при miss скачивает через тот же info
dict. Если info JSON отсутствует после рестарта, повреждён или устарел, воркер
безопасно делает обычное повторное извлечение.

Info-файл не хранится в БД, не является долговременным кешем и удаляется общим
cleanup вместе с медиа. Cookie-варианты перебираются в прежнем порядке;
санитизированный info содержит нужные HTTP headers, а downloader получает те же
cookie options. Ошибка одного варианта не отменяет существующий fallback.

### 5. Быстрый путь подготовки MP4

Первичный probe сохраняется, потому что он защищает Telegram-совместимость.
FFmpeg не запускается, если одновременно выполняются условия:

- контейнер уже `.mp4`;
- есть видео и аудио;
- видео H.264/AVC, pixel format `yuv420p` или не требует исправления;
- аудио AAC;
- sample aspect ratio равен `1:1` или отсутствует;
- отсутствует rotation metadata.

В этом случае `_prepare_telegram_video()` возвращает исходный путь и probe.
HEVC, WebM/MKV/MOV, не-AAC audio, rotation, неправильный SAR/pixel format и
слайд-шоу продолжают использовать текущий remux/transcode.

Если Telegram отклоняет файл, который прошёл быстрый путь, воркер один раз
выполняет принудительную нормализацию и повторяет доставку. Повтор разрешён только
для локального файла, который ещё не был успешно отправлен; cache `file_id`
обрабатывается отдельной логикой из предыдущего раздела.

### 6. Selective storage

Private/group cache-miss сначала отправляется пользователю локальным файлом.
Полученный из успешного сообщения `file_id` сохраняется в `VideoCache`, поэтому
предварительная полная загрузка в storage-канал не нужна.

Storage используется только для первого inline cache-miss: inline message нельзя
заменить локальным multipart-файлом, поэтому воркер загружает файл в
`STORAGE_CHAT_ID`, получает `file_id`, а затем редактирует inline message.

Фоновая репликация private/group в storage не добавляется: она не нужна для
повторной отправки bot-scoped `file_id` и увеличила бы трафик и время жизни файла.
`storage_message_id` остаётся nullable для совместимости.

### 7. Короткие БД-сессии

Воркер разделяется на три слоя:

1. `_load_next_job()` открывает сессию, выбирает следующую запись, копирует поля
   в неизменяемый `QueueJob` и закрывает сессию.
2. Download, metadata, FFmpeg, storage и Telegram работают без активной
   SQLAlchemy-сессии.
3. Небольшие helpers с отдельными сессиями выполняют cache lookup, создание
   music deep-link, успешное завершение, удаление или обработку ошибки.

Поскольку проект официально запускает один worker в одном процессе, запись
остаётся в таблице до завершения. При падении она будет выбрана снова после
рестарта, как и сейчас. Atomic claim/lease и multi-process semantics в эту работу
не входят; это явно остаётся ограничением README.

Music-job также не держит сессию во время загрузки, FFmpeg chunks и Shazam.
Состояние `MusicRequest` читается до внешней работы и обновляется после неё новой
короткой транзакцией.

### 8. Пробуждение и приоритет очереди

После успешного enqueue выставляется процессный `asyncio.Event`. Пустой worker:

1. очищает event;
2. повторно проверяет БД, чтобы не потерять enqueue между SELECT и `clear()`;
3. ждёт event с резервным timeout;
4. после timeout снова сканирует persistent queue.

Так локальный enqueue будит worker немедленно, а timeout сохраняет поддержку
заданий, появившихся до запуска или внесённых другим инструментом.

При выборе следующей записи обычные video jobs сортируются перед music jobs, а
внутри каждого класса сохраняется порядок по `id`. Уже начатое распознавание не
прерывается, но ожидающая музыка больше не стартует перед ожидающим видео.
Параллельный music-worker не создаётся.

### 9. Логи и измерения

`db/session.py` переводится на `echo=False`. `main.py` использует
`RotatingFileHandler(maxBytes=45_000_000, backupCount=1)`, сохраняя суммарный
предел около 90 МБ для `bot.log` и одной резервной копии.

Для каждого job INFO-лог содержит идентификатор и длительности monotonic-этапов:

- queue wait;
- cache lookup и результат hit/miss;
- canonicalize/inspect metadata;
- download и выбранный fallback;
- probe/prepare и признак FFmpeg bypass;
- split и число попыток;
- storage upload;
- user delivery;
- total.

Логи не содержат cookies, токен бота, полные HTTP headers или персональные данные,
кроме уже используемых технических chat/job identifiers.

## Потоки данных

### Private

1. Пользователь отправляет URL и выбирает режим.
2. Handler проверяет кеш до quality inspection.
3. Hit: `file_id` доставляется напрямую с выбранным описанием/спойлером; конец.
4. Invalid `file_id`: кеш удаляется, запрос продолжает miss-path.
5. Miss: одна inspection строит quality options и info snapshot.
6. Для малого видео сразу создаётся placeholder, включается пятисекундный таймер
   и job записывается в очередь вместе с временным info JSON.
7. Для большого видео существующее меню показывает варианты из той же inspection;
   после выбора создаются placeholder, пятисекундный таймер и job с тем же info
   snapshot и выбранным `format_id`.
8. Воркер просыпается, скачивает, при необходимости нормализует/делит, отправляет
   пользователю, сохраняет новый `file_id` и удаляет job/temp files.

### Group

1. Handler канонизирует URL и проверяет кеш.
2. Hit: отвечает видео по `file_id` на исходное сообщение без placeholder/queue.
3. Miss: создаёт рекламный placeholder, enqueue и timer на пять секунд.
4. Воркер выполняет одну inspection+download и редактирует placeholder.

### Inline

1. `ChosenInlineResult` получает canonical URL и проверяет кеш.
2. Hit: немедленно редактирует inline message по `file_id`.
3. Miss: enqueue; worker выполняет inspection+download.
4. Новый файл один раз отправляется в storage для получения `file_id`, после чего
   inline message редактируется и cache row сохраняется.

## Обработка ошибок

- Cache lookup failure не ломает запрос: handler переходит к queue-path.
- Невалидный `file_id` удаляет только соответствующую строку и автоматически
  инициирует повторную загрузку.
- Временная Telegram-ошибка сохраняет кеш и следует существующей retry/error UX.
- Повреждённый или устаревший info JSON приводит к обычному re-extract.
- Ошибка direct MP4 delivery разрешает ровно одну принудительную нормализацию.
- Ошибки yt-dlp сохраняют gallery-dl fallback и cookie-варианты.
- Cleanup удаляет media, `.info.json`, части и временные remux-файлы во всех
  успешных и ошибочных ветках.
- Ошибка cache/queue финализации логируется; исходная queue row не удаляется до
  подтверждённой доставки, чтобы перезапуск мог повторить работу.

## Тестирование

Изменения выполняются через TDD. Добавляются тесты:

1. Cache identity для TikTok video/photo, Instagram reel и неизвестного URL.
2. Private cache hit соблюдает каждый delivery mode, не вызывает quality probe,
   enqueue, sleep, downloader, FFmpeg или storage.
3. Group и inline cache hit не создают queue row и доставляются по `file_id`.
4. Невалидный `file_id` удаляет кеш и продолжает enqueue; forbidden/rate-limit и
   другие ошибки кеш не удаляют.
5. Cache miss использует рекламную задержку пять секунд.
6. Успешный private/group/inline miss выполняет не более одной extractor-фазы;
   stale info JSON безопасно вызывает re-extract.
7. H.264/AAC/yuv420p MP4 обходит FFmpeg; HEVC, rotation, WebM и несовместимый
   audio продолжают нормализоваться.
8. Private/group не выполняют storage pre-upload; первый inline miss выполняет
   ровно один upload в storage.
9. БД-сессия закрыта до искусственно задержанных download и Telegram await.
10. Event будит пустой worker без секундного ожидания и не теряет race enqueue.
11. Ожидающее обычное видео выбирается раньше ожидающего music job, FIFO внутри
    классов сохраняется.
12. SQL echo отключён, logging использует ограниченную ротацию.
13. Существующие media preparation, quality, caption, links, music и error tests
    продолжают проходить, включая незакоммиченный пользовательский error-test.

Нестабильные wall-clock assertions не используются. Производительность
проверяется счётчиками вызовов, контролируемыми event/future и логируемыми
этапами. Реальные p50/p95 измеряются отдельно на production только после явного
разрешения на развёртывание.

## Критерии готовности

- Валидный cache hit создаёт ноль queue rows, extractor-вызовов, FFmpeg-процессов
  и storage uploads.
- Cache hit не имеет искусственной рекламной задержки.
- Cache miss удерживает рекламу минимум пять, а не пятнадцать секунд.
- Обычный успешный miss использует одну extractor-фазу при свежем info snapshot.
- Совместимый MP4 не переписывается FFmpeg.
- Сетевые/FFmpeg операции выполняются без открытой SQLAlchemy-сессии воркера.
- Ожидающие video jobs имеют приоритет над ожидающими music jobs.
- Одновременно выполняется только одна тяжёлая media-задача.
- Все автоматизированные тесты, compile check и `git diff --check` проходят.
- Пользовательские незакоммиченные изменения не перезаписаны и не попадают в
  несвязанный commit.

## Риски и смягчение

- Прямой MP4 может выявить редкую несовместимость Telegram. Смягчение: строгий
  probe и одноразовая принудительная нормализация до показа ошибки.
- Info URL может истечь. Смягчение: встроенный fallback `download_with_info_file`
  к `webpage_url` и очистка snapshot после job.
- Priority нарушает единый FIFO между музыкой и видео. Это намеренное решение:
  обычная доставка получает более высокий QoS, FIFO сохраняется внутри класса.
- Cache row может устареть. Смягчение: узкая классификация invalid-file-id,
  автоматическая инвалидация и прозрачный переход к queue-path.
- Короткая сессия без durable claim не поддерживает несколько процессов. Это не
  регрессия: один экземпляр остаётся документированным условием запуска.
- Пять секунд рекламы всё ещё задают нижнюю границу нового быстрого видео. Cache
  hit намеренно исключён из этой границы по утверждённому UX.
